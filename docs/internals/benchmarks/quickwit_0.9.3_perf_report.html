Cold-Cache Methodology & Fairness Notes
  • True Disk-Cold (posix_fadvise(POSIX_FADV_DONTNEED) + engine caches dropped/zeroed): Used for Quickwit SearchBench 100M and the dedicated ClickBench 10M Quickwit vs ClickHouse disk-cold shootout. Quickwit was verified reading 1.48 GB directly from NVMe via /proc/<pid>/io with all 4 searcher caches set to 0B; ClickHouse executed SYSTEM DROP MARK / UNCOMPRESSED / QUERY CACHE plus fadvise eviction before every query.
  • App-Cold (Run 1, OS page cache warm): Local SearchBench runs for SereneDB 26.09.1 and ClickHouse 26.8.2.7 were captured on this exact workstation without NOPASSWD sudo, so /proc/sys/vm/drop_caches was skipped (making their cold numbers OS-warm relative to Quickwit's disk-cold). Big5 Run 1 ran on freshly started servers with request_cache=false (OpenSearch/ES Run 1 includes Lucene/JVM warmup).

8. Key Architectural Takeaways & Next Opportunities

Engineering roadmap

1. Trimmed Doc Mapping Cuts Wide-Table Size by 26% with Zero Latency Loss

On ClickBench (105 columns), keeping only the 14 filter/search columns indexed (including URLHash & RefererHash) while keeping all 105 columns fast: true and stored: true reduced inverted index files (.idx + .term) by ~80%, shrank total storage from 3.32 GB → 2.45 GB, cut ingest to 61.1 s, and kept Hot latency at 432 ms (geomean 7.68 ms) with 100% verbatim row retrieval on Q20/Q24/Q25.

2. Synthetic _source from .fast Is the Next 2× Storage Win

In the trimmed ClickBench index, Tantivy's columnar .fast holds all 105 columns in just ~0.68 GB (less than half of ClickHouse's 1.44 GB), while .store takes ~1.10 GB (56%) solely for fetch_docs. Reconstructing returned rows directly from .fast columns would bring ClickBench down to ~1.0 GB while preserving full size: 100 row retrieval.

3. docs_clustering Helps Unsorted Analytics, Hurts Pre-Grouped Logs

Clustering ClickBench by CounterID → EventDate+RegionID → UserID improved Hot latency -4.0% (427 → 410 ms) and Run 1 -10%. On Big5 CloudWatch logs, however, clustering fragmented natural log_group/log_stream RLE runs (+4.1% latency, 2.36× slower ingest).

4. Clear Next Targets vs SereneDB 26.09.1

Across all 77 SearchBench queries, Quickwit dominates BM25 top_k (2.91× cold / 1.74× hot), boolean counts (1.92× / 1.85×), and aggregations (1.51×) at 2.36× smaller footprint. SereneDB's remaining lead is concentrated in count_pattern (regex/wildcard: 113 vs 218 ms) and recent_* doc fetches (85 vs 110 ms).
